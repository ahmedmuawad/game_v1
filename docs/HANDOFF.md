## أول مهمتين

### 1. تشغيل على الجهاز وتشخيص العرض
الموبايل متصل بالـUSB ووضع debug مفعّل. عايز:
- npm run dev -- --host  وأجرب من متصفح الموبايل
- وبعدين npx cap add android ثم npm run cap:android للتطبيق الأصلي
- استخدم chrome://inspect لفتح DevTools على WebView وتشخيص أي مشكلة عرض

في الجلسة السحابية اختبرت 6 مقاسات شاشة وكلها سليمة، فالأرجح إن مشكلة
العرض كانت في إطار المعاينة لا في التطبيق — أكّد ده على الجهاز الحقيقي.

### 2. واجهة الحلقة اليومية
ده أهم بند في docs/QUALITY_REVIEW.md §7. المنطق كامل ومختبَر في
src/systems/daily.ts (12 اختبار) لكنه غايب تمامًا عن الشاشة: اللاعبة
مش شايفة سلسلتها ولا مهامها ولا هدية اليوم. يعني أقوى محرك عودة يومي
معطّل عمليًا — وده بالظبط العيب الموثّق في المنافسين واللي المنتج ده
اتبنى عشان يتفاداه.

## قواعد لا تُكسر
1. صفر نصوص في المكوّنات — كل نص له مفتاح في src/i18n/strings.ts أو
   حقل {ar, en} في المحتوى
2. خصائص CSS المنطقية حصريًا (margin-inline-start لا margin-left)
3. المنطق في systems/ بلا React ولا وصول للمخزن
4. المحتوى بيانات لا كود — إضافة فصل أو قطعة أزياء متحتاجش بناء جديد
5. لا eval في تقييم شروط القصة
6. خط الإنتاج لا يُصدّر شخصية بلا ملابس أبدًا
7. قيم التوازن في systems/config.ts فقط

## محرّمات المنتج
لا صناديق غنائم ولا أي عشوائية مدفوعة · لا بيع اختيارات سردية · لا بيع
استعادة السلسلة · لا شات ولا نص حر بين اللاعبين · الهوية (بشرة/شعر/
عيون) مجانية دائمًا · إعلانات غير مخصّصة فقط بسقف يومي صارم.
السبب في docs/DECISIONS.md#D-002 — الجمهور كله قاصرون.

## طريقة الشغل
- اشتغل بمعالم: هدف → تنفيذ → تحقّق فعلي → توثيق → commit
- **تحقّق فعلي مش افتراضي:** شغّل التطبيق وصوّره، شغّل الاختبارات،
  وقيس بدل ما تتخيّل. أربع أعطال جوهرية في المشروع ده اتكشفت بالقياس
  ومكانش ممكن تتشاف بالعين
- بعد كل معلم حدّث docs/QUALITY_REVIEW.md بمراجعة نقدية صادقة
- ادفع على نفس الفرع claude/livi-master-platform-plx75g

ابدأ بقراءة الملفات وقوللي خطتك قبل ما تنفّذ.
